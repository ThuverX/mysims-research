# Vault

<KingdomSpecific />

The vault is EA's **AttribSys** database. It holds most of MySims Kingdom's game data: characters, worlds and the
objects placed in them, rewards, quests, Create-a-Sim parts, cameras and more.

A vault is a pair of files:
- `.vlt` is the **schema**: types (primitive and compound) and classes (sets of typed fields).
- `.bin` holds the **collections**: named records of one class. A collection can inherit from a parent collection of
  the same class, and it stores only the fields it sets.

## Location

The files are in `GameData/Vaults/`:

| File                          | Description                                                   |
|-------------------------------|---------------------------------------------------------------|
| `attribdb.vlt`/`attribdb.bin`   | The vault the game loads (12,361 collections)                 |
| `attribdbz.vlt`/`attribdbz.bin` | A second vault, mostly a subset of `attribdb` (10,291 collections) |
| `attribdb.log`, `dbexporter.log` | Exporter logs that list every type, class, field and collection as `name[0xHASH]` |

## Hashing

Every id (type, member, class, field, collection) is the [FNV32](../FNV) hash of a name, computed over the
**lowercased** ASCII name. There are two exceptions:
- `Text` values hash their string **without** lowercasing.
- Dynamic array elements use a derived key (see [Dynamic arrays](#dynamic-arrays)).

The names themselves are not stored in the vault. The exporter logs next to the vault files are the best source for
them.

All values are little-endian.

## `.vlt` (schema)

### Header

0x28 bytes.

| Offset | Type     | Name          | Notes                |
|--------|----------|---------------|----------------------|
| 0x00   | u32      | endian marker | always 1             |
| 0x04   | char[4]  | magic         | `TLAV`               |
| 0x08   | u32      | version       | 3                    |
| 0x0C   | u32      | size          | not used             |
| 0x10   | u32      | class_count   |                      |
| 0x14   | u32      | type_count    | 112 in the shipped vaults |
| 0x18   | u8[16]   | reserved      | zeros                |

### Types

`type_count` type records follow, 40 bytes each:

| Offset | Type   | Name         | Notes                                           |
|--------|--------|--------------|-------------------------------------------------|
| 0x00   | u32    | type         | hash of the type name, e.g. `EA.Reflection.Float` |
| 0x04   | u16    | size         | bytes per value                                 |
| 0x06   | u16    | flags        | unknown                                         |
| 0x08   | u16    | align        |                                                 |
| 0x0A   | u16    | member_count | 0 for primitive types                           |
| 0x0C   | u8[28] | runtime      | `u32 0` and three u64 pointers                  |

Next come the members. For each type with `member_count > 0`, in type order, there are three parallel arrays with no
padding between them:

| Type      | Name                                           |
|-----------|------------------------------------------------|
| u32 × m   | member name hashes                             |
| u16 × m   | member type indices (into the type list)       |
| u16 × m   | member counts (element count; 0 or 1 = single) |

At runtime, the three pointers in a type's `runtime` bytes point at these arrays.

:::warning[Not every listed member is stored]
In 14 compound types, the listed members take up more bytes than the type's `size`. Each *handle* member is followed by
one plain `UInt32` or `UInt64` member for each member the handle has. Handle members are compounds such as
`Attrib.CollectionKey`, `MySims.AssetSpec`, `Attrib.RefSpec` and `MySims.HALString`. The extra members are a runtime
copy of what the handle resolves to and are **not in the file**. Skip them and the type fits its `size` exactly.

For example, `MySims.PaintInfoEntry` lists 7 members, but only 4 are stored:

| Offset | Type                   | Meaning                                  |
|--------|------------------------|------------------------------------------|
| 0x00   | `MySims.AssetSpec`     | material                                 |
| 0x08   | `MySims.AssetSpec`     | material (the same, in every value seen) |
| 0x10   | `Attrib.CollectionKey` | paint (`default`, `coral`, …)            |
| 0x14   | `UInt32`               | mesh index                               |
:::

### Classes

After the members come `class_count × u64` class pointers (runtime only, ignored) and then the classes. Each class is
a 40-byte header, its fields, and a trailer:

| Offset | Type                  | Name        | Notes                                                      |
|--------|-----------------------|-------------|------------------------------------------------------------|
| 0x00   | u32                   | class       | hash of the class name, e.g. `world`                       |
| 0x04   | u32                   | unknown     | low u16 is 0                                               |
| 0x08   | u16                   | field_count |                                                            |
| 0x0A   | u16                   | unknown     |                                                            |
| 0x0C   | u8[28]                | runtime     | `u32 0`, a u64 pointer, two unknown u16, 12 zero bytes     |
| 0x28   | Field × field_count   | fields      | 32 bytes each                                              |
| …      | u8[]                  | trailer     | unknown; runs in 8-byte steps to the next class header     |

Field (32 bytes):

| Offset | Type   | Name       | Notes                                 |
|--------|--------|------------|---------------------------------------|
| 0x00   | u32    | field      | hash of the field name                |
| 0x04   | u32    | type       | type hash                             |
| 0x08   | u16    | size       | bytes per element                     |
| 0x0A   | u16    | flags      | see below                             |
| 0x0C   | u16    | count      |                                       |
| 0x0E   | u16    | align      |                                       |
| 0x10   | u16    | type_index | index into the type list              |
| 0x12   | u8[14] | runtime    | six zero bytes and a u64 pointer      |

Field flags:

| Bit    | Name         | Meaning                                                                        |
|--------|--------------|--------------------------------------------------------------------------------|
| 0x0004 | INHERITABLE  | taken from the parent collection when not set                                  |
| 0x0008 | ARRAY        |                                                                                |
| 0x0010 | FIXED_ARRAY  | with ARRAY: a contiguous fixed array; without it, ARRAY is a dynamic array     |
| 0x0040 | READ_ONLY    |                                                                                |
| 0x0200 | BY_OFFSET    | the entry holds an offset into the collection's data                           |
| 0x0400 | FORCED       | always present (layout fields such as `Position`)                              |

There is no marker for where a class ends. To find the next class header, step through the trailer 8 bytes at a time
and look for this shape:
- a nonzero u32,
- `u16 0` at +4 and `u32 0` at +12,
- and either a field count of zero at +8, or a first field whose type (at +44) is a known type hash.

The last class's trailer runs to the end of the file. Trailers seem to hold
`(hash("AttribClass"), class)` pairs.

## `.bin` (collections)

### Header

Collections start at 0x144.

| Offset | Type  | Name             | Notes          |
|--------|-------|------------------|----------------|
| 0x00   | u32   | endian marker    | always 1       |
| 0x04   | char[4] | magic          | `NIBV`         |
| 0x08   | u32   | version          | 5              |
| 0x0C   | u32   | collection_count |                |
| 0x10   | u32   | unknown          |                |
| 0x14   | u32   | —                | 0              |
| 0x18   | u32   | unknown          |                |
| 0x1C   | u32   | —                | 0              |
| 0x20   | u32   | string_count     |                |
| 0x24   | u32   | —                | 0              |
| 0x28   | u32   | unknown          |                |
| 0x2C   | u8[]  | reserved         | zeros up to 0x144 |

### Collections

Collections are **byte-packed**, with no alignment between records:

| Offset | Type                     | Name           | Notes                                                   |
|--------|--------------------------|----------------|---------------------------------------------------------|
| 0x00   | u32                      | collection     | hash of the collection name                             |
| 0x04   | u32                      | vault          |                                                         |
| 0x08   | u32                      | class          | class hash                                              |
| 0x0C   | u32                      | parent         | key of the parent collection of the same class; 0 = none |
| 0x10   | u16                      | flags          | unknown                                                 |
| 0x12   | u16                      | unknown        |                                                         |
| 0x14   | u32                      | —              | 0                                                       |
| 0x18   | u16                      | unknown        |                                                         |
| 0x1A   | u16                      | unknown        |                                                         |
| 0x1C   | u16                      | entry_count    | entries in use                                          |
| 0x1E   | u16                      | entry_capacity | entries stored                                          |
| 0x20   | u16                      | data_used      | bytes of the data block that hold values                |
| 0x22   | u16                      | data_capacity  | size of the data block                                  |
| 0x24   | Entry × entry_capacity   | entries        | the first `entry_count` are used, the rest are padding  |
| …      | u8[data_capacity]        | data           |                                                         |

Entry (8 bytes):

| Offset | Type  | Name  | Notes                                             |
|--------|-------|-------|---------------------------------------------------|
| 0x00   | u32   | field | field hash, or a dynamic array element key        |
| 0x04   | u8[4] | value | inline value, or `u16 offset; u16 count`          |

### String table

The string table comes after the last collection:

| Type                                   | Name  | Notes                                                             |
|----------------------------------------|-------|-------------------------------------------------------------------|
| `{u32 hash; u32 offset}` × string_count | index | hash of the text (case-sensitive); offset is relative to the end of the index |
| NUL-terminated strings                 | text  | UTF-8                                                             |
| u8[]                                   | tail  | unknown, up to the end of the file                                |

## Patterns

[ImHex](https://imhex.werwolv.net/) patterns for both files. Load each pattern on its own file type.

### `.vlt`

The class trailers are found with the search described in [Classes](#classes).

```cpp
import std.core;
import std.mem;
import type.base;

struct VltHeader {
    u32 endian;
    char magic[4]; // TLAV
    u32 version;   // 3
    u32 size;
    u32 classCount;
    u32 typeCount;
    padding[16];
};

struct VltType {
    type::Hex<u32> typeHash;
    u16 size;
    u16 flags;
    u16 align;
    u16 memberCount;
    padding[28];
};

// The member arrays of one type. Empty for types without members.
struct VltMembers {
    u32 typeIndex = std::core::array_index();
    u16 m = std::mem::read_unsigned(0x28 + typeIndex * 40 + 0x0A, 2);
    type::Hex<u32> names[m];
    u16 typeIndices[m];
    u16 counts[m];
};

struct VltField {
    type::Hex<u32> field;
    type::Hex<u32> typeHash;
    u16 size;
    type::Hex<u16> flags;
    u16 count;
    u16 align;
    u16 typeIndex;
    padding[14];
};

fn is_known_type(u32 hash) {
    u32 typeCount = std::mem::read_unsigned(0x14, 4);
    for (u32 i = 0, i < typeCount, i = i + 1) {
        if (std::mem::read_unsigned(0x28 + i * 40, 4) == hash)
            return true;
    }
    return false;
};

fn is_class_start(u128 at) {
    if (at + 48 > std::mem::size()) return true; // stop at the end of the file
    if (std::mem::read_unsigned(at, 4) == 0) return false;
    if (std::mem::read_unsigned(at + 4, 2) != 0) return false;
    if (std::mem::read_unsigned(at + 12, 4) != 0) return false;
    if (std::mem::read_unsigned(at + 8, 2) == 0) return true;
    return is_known_type(std::mem::read_unsigned(at + 44, 4));
};

struct VltClass {
    u32 classIndex = std::core::array_index();
    type::Hex<u32> classKey;
    u32 unk0;
    u16 fieldCount;
    u16 unk1;
    padding[28];
    VltField fields[fieldCount];
    if (classIndex + 1 < std::mem::read_unsigned(0x10, 4))
        u64 trailer[while(!is_class_start($))];
    else
        u8 trailer[while(!std::mem::eof())];
};

struct VltFile {
    VltHeader header;
    VltType types[header.typeCount];
    VltMembers members[header.typeCount];
    u64 classPointers[header.classCount];
    VltClass classes[header.classCount];
};

VltFile file @ 0x00;
```

### `.bin`

Dynamic array elements need the logic described in [Dynamic arrays](#dynamic-arrays), so this pattern shows the raw
entries and data.

```cpp
import type.base;

struct BinHeader {
    u32 endian;
    char magic[4]; // NIBV
    u32 version;   // 5
    u32 collectionCount;
    u32 unk0;
    u32;
    u32 unk1;
    u32;
    u32 stringCount;
    u32;
    u32 unk2;
    padding[0x144 - 0x2C];
};

struct Entry {
    type::Hex<u32> field;
    u8 value[4];
};

struct Collection {
    type::Hex<u32> key;
    type::Hex<u32> vault;
    type::Hex<u32> classKey;
    type::Hex<u32> parentKey;
    type::Hex<u16> flags;
    u16 unk0;
    u32;
    u16 unk1;
    u16 unk2;
    u16 entryCount;
    u16 entryCapacity;
    u16 dataUsed;
    u16 dataCapacity;
    Entry entries[entryCapacity];
    u8 data[dataCapacity];
};

struct BinFile {
    BinHeader header;
    Collection collections[header.collectionCount];
};

BinFile file @ 0x00;
```

## Values

To read a field's value, find its hash among the collection's entries. The field definition comes from the
collection's class in the schema.

- **Inline** (no BY_OFFSET flag): the value is the entry's 4 bytes. Only `min(size, 4)` bytes are used.
- **BY_OFFSET**: the entry holds `u16 offset; u16 count`. The value is `size` bytes at `offset` in the data block. For
  an array, the value is `count` elements of `size` bytes each, stored back to back.
- **Dynamic arrays** (ARRAY without FIXED_ARRAY): see below.
- **Undefined entries**: some entries are neither a field of the class nor an array element. Their bytes run from the
  entry's offset to the next value's offset in the data. If the offset is past `data_used`, the value is the entry's
  4 bytes.

### Dynamic arrays

The field's own entry holds `u16 offset; u16 count`. The elements are stored in one of two ways:

- **Inline**, when the field has no element entries. There are `count` elements at `offset`, just like a fixed array
  (e.g. `paint_kit.paints`, `ui_inventory.Item_List`).
- **As entries of their own**. Each element is keyed `fnv1(seed + "[%03d]")` and holds `u16 offset; u16 index`. The
  FNV-1 state `seed` is continued over a suffix such as `[007]`.

The seed is the same for every element of a field, but it is **not** the field's hash, and how it is derived is
unknown. It can be recovered from the element keys by undoing the suffix with the inverse of the FNV prime. Then each
seed can be matched to a field: look for collections where the elements under one seed fit exactly one array, meaning
every index is below the array's count and the offsets step by the field's size.

Some arrays store index 0 for **every** element (`island.Ambients`, `trevor_trevor`'s `AlternateBodyModel`). The seed
recovered from index 0 is then wrong, and it can even match another field's seed. Some things that help:
- Treat the elements under one seed as a group. A group belongs to an array whose count equals the group's size and
  whose element size equals the step between the group's offsets.
- Arrays with the same count and element size take their groups in field order. Element blocks are stored in the data
  in field (hash) order.
- Swapping the last digit of two elements (0↔1, 2↔3, …) gives another seed that both elements share, because the
  index digits are XORed into the hash. So the key alone can't tell you the order of the elements. Use the stored
  indices when they differ, and otherwise the offsets.

### Types

Types by name (the name's hash is stored):

| Type                                                     | Value                                                                    |
|----------------------------------------------------------|--------------------------------------------------------------------------|
| `EA.Reflection.Bool`                                     | `u8 != 0`                                                                |
| `EA.Reflection.Int8` / `Int16` / `Int32` / `Int64`       | signed integer                                                           |
| `EA.Reflection.UInt8` / … / `UInt64`                     | unsigned integer                                                         |
| `EA.Reflection.Float`                                    | f32                                                                      |
| `EA.Reflection.Text`                                     | u32 hash into the `.bin` [string table](#string-table)                   |
| `Attrib.Types.Vector2` / `Vector3` / `Vector4` / `Quaternion` / `FloatColour` | f32 × n                                             |
| `Attrib.CollectionKey`                                   | u32 collection key; the class is implied by the field                    |
| `Attrib.RefSpec` (`0x65833771`)                          | `u32 class; u32 collection`                                              |
| `MySims.AssetSpec` (`0xD7CEB540`)                        | u64 resource instance (see [Resource Key](../ResourceKey))               |
| `MySims.HALString`                                       | one member (`0xA1954553`) holding a record id in `TextEAGLE/pc/eng_us.str` (see [Str](./Str)) |
| `GameObject.ComponentSet`                                | two u64 bit sets                                                         |
| other compound types                                     | stored members in order, each aligned to its type's `align`, with `count` elements |

## Inheritance

If a collection doesn't store a field, look it up in its parent (the collection of the same class whose key is
`parent`), and so on up the chain. For example, most placed objects inherit their `Model` from a definition collection.

## Unknowns

- `.vlt`: the header `size`, type `flags`, two u16 in each class header, and the class trailers.
- `.bin`: the header words at 0x10, 0x18 and 0x28; the collection `vault` and `flags` fields and three u16; the tail
  after the strings.
- How a dynamic array's element seed is derived from the field. It is not the hash of the field name, in either case,
  on its own or combined with the class.
- `MySims.CASAssetInfo` member names.
